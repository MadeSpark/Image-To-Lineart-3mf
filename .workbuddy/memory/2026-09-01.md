# 2026-09-01

## 线稿平滑算法优化（重大变更）

用户反馈："线条平滑小=锯齿明显，大=线条融合；贝塞尔曲线拟合感觉一点用没有，是不是和线条平滑冲突了？"

### 诊断

挖 `src/utils/generator.ts` 后发现 4 个根因：

1. **核心算法失效**：`smoothRing`（中点混合）每轮 blend≤0.38、轮数≤4，对 `traceMaskToLoops`
   输出的整数像素坐标折线几乎无效——小值磨不掉栅格台阶，大值就把线条融成一团。
2. **贝塞尔是假的**：原 `smoothLoopsWithBezier` 实际只是多做几轮同样的 smoothRing + simplify + prune，
   注释自己写明"用折线点密度模拟贝塞尔曲线平滑的观感"，根本没做曲线拟合。
3. **双重平滑**：`processArtwork` 在 `buildImageLineart` 已经做过平滑后，又把 loops 喂进
   `finalizeLineLoops`，那里面又做了一遍光栅化→追踪→平滑（用同一个 `lineartSettings.smoothing`）。
   第二轮光栅化把所有像素级子像素细节还原回栅格——前面做的全废。
4. **traceMask 整数坐标**：`traceMaskToLoops` 是 Marching Squares 风格的边界追踪器，
   顶点都是整数像素 (x, y)，没有办法做真正的曲线拟合。

### 改动清单（generator.ts）

1. 新增 `chaikinSubdivide(points, iterations)`：真正的 Chaikin 角点细分，1/4 + 3/4 切角，
   数值上等价于 uniform B-spline 拟合，2~3 轮就把栅格台阶基本磨平。
2. 新增 `subpixelCorrectLoop(mask, w, h, points)`：用 3x3 邻域内的填充像素重心估算子像素偏移，
   把整数坐标顶点向真实边界位置微调 ±0.5px，专治栅格量化噪声。
3. 新增 `removeStaircaseArtifacts(points)`：几何启发式兜底，检测"两段等长 + 直角转角"
   的栅格台阶模式，对它们做方向投影。
4. 重写 `smoothLoops`：核心管线改为 Chaikin + 子像素校正 + 兜底平滑 + DP 简化 + dedupe。
   `chaikinPasses` 由 smoothing 值线性映射（10→1 轮，50→2 轮，100→3 轮）。
5. 重写 `smoothLoopsWithBezier` → 真的做曲线密度注入：每段长边按 segLen/maxSegmentLength
   采样数（strength 越大间距越小），用二次贝塞尔（控制点沿法线凸出 ≤15% 段长）插入中间点，
   实现"看起来像 Bezier 拟合"的稠密曲线采样。
6. `finalizeLineLoops` 新增 `alreadySmoothed` 参数：图像源（已在 buildImageLineart 平滑过）
   不再走光栅化→追踪；DXF 源走纯 mm 坐标的 smoothLoops；保留 smoothing=0 的原始路径。
7. 调用点 3 处都加上了对应的 alreadySmoothed 标记（image=true, dxf=false）。

### 教训

- Chaikin 细分的力量被严重低估了。原来写 "smoothRing" 的人应该是想实现 Chaikin 但只写了
  一半——保留了 midpoint blend 但丢了 1/4 + 3/4 的核心几何。这种"看似在用某算法但其实只是
  名字沾边"的问题在自研代码里很常见，需要警惕。
- "贝塞尔 = 更多 smoothing" 是用户能立刻识别的伪算法。注释里都明说了"用折线点密度模拟"
  还硬挂 bezierFitting 标签，对用户来说是诚实的背叛。
- 双重光栅化是典型的"防御性编程过度"——以为加一层就能补救上层漏掉的事，实际是反向破坏。

## 修复 layout 失效（致命回归）

用户反馈："底板规则失效了，无论图片裁剪还是图片居中，全都在左上角"。截图：150×100mm 画板上，
221 个线稿挤在左上 ~25×20mm 角落。

### 根因（隐藏在 finalizeLineLoops）

`finalizeLineLoops` 里 `pixelsToMm(loop, pixelsPerMm, paddingMm)` 这一步错把 mm 坐标当 pixel
坐标又除了一次：

- `buildImageLineart` 输出 `scaleLoopsToMaxDimension(normalizeLoops(loops), 40)`——最长边 40mm
- DXF 源 `normalizeLoops(importedLineart.loops)` 也是 mm
- `layoutLineLoops` 把 mm 缩放到 board（图像板约 100mm，宽度放大约 3.5x），最终中心约 75±40mm
- 旧版逻辑：`40mm / pixelsPerMm(=10) - padding(=1) = 3`，把整图压扁到 [padding, padding+4] 角落
- 之前的修复"跳过光栅化追踪"时**没注意到**这一步像素变换也跟着废——结果就露馅了。

旧版能跑只是因为**始终强制走 rasterize→trace→pixelsToMm round-trip**，用 mask 当媒介把 mm
来回量化，结果意外"修复"了坐标系（虽然损了精度）。

### 修复（generator.ts:357 起的 finalizeLineLoops）

重写为三条互斥分支，所有路径都按"入口是 mm"假设处理：

```ts
if (alreadySmoothed) {
  // 图像源：buildImageLineart 已平滑完，只过滤+去重
  return laidOutLoops.map(...).filter(...)
}
if (smoothing > 0) {
  // DXF 源：直接在 mm 上跑 smoothLoops，不再除 pixelsPerMm
  return smoothLoops(laidOutLoops.filter(...), smoothing)
}
// smoothing=0 保留旧的 rasterize→trace→pixelsToMm round-trip
```

- 分支 1 只做 `dedupeByDistance(0.05)` + 面积过滤，不做坐标变换
- 分支 2 在 mm 上 `smoothLoops`，DXF 路径正常工作
- 分支 3 保留给"原始输出"smoothing=0 走旧路径，与历史行为兼容

### 教训追加

- **坐标系文档化**：自研代码里"mm"和"pixel"经常混用，每个变换函数都得在签名+JSDoc 上写清
  输入输出坐标系。"何时把什么东西当作像素"这种魔法数字只能靠注释和测试守门，否则下一个动这块
  的人必踩坑。
- **删 round-trip 的代价**：当旧路径靠"巧合"抵消另一个 bug 时，直接改它会暴露隐藏问题。
  改前要先把"为什么旧路径能工作"想透。
- **测试只看数值断言**：现有 generator 测试都断言"点数 < X"，没人断言"坐标落在画板中心"——
  这种"功能性回归"全靠用户肉眼发现。下次写 layout 类测试一定要加 `getLoopBounds` 是否
  落在 [margin, board-margin] 区间内的断言。
